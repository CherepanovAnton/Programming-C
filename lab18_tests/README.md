# 📁 Лабораторная работа №18: Модульное тестирование ПО. Нативный Unit-тестинг через CTest

Лабораторная работа посвящена изучению жизненного цикла разработки ПО (SDLC), методологий обеспечения качества и практической реализации автоматизированного модульного тестирования (Unit Testing) с использованием встроенного фреймворка `CTest` в экосистеме `CMake`.

### 🎯 Задача работы (Выполнено на практике)
* **Разработать безопасный вычислительный модуль (`factorial.c`, `factorial.h`)**: Написать функцию вычисления факториала `safe_factorial`, устойчивую к некорректным входным данным (отрицательные числа) и защищенную от арифметического переполнения типов данных (ограничение $n \le 12$).
* **Спроектировать тестовый стенд (`tests.c`)**: Реализовать автоматическую проверку утверждений (assertions) через анализ аргументов командной строки без использования тяжелых сторонних тестовых библиотек.
* **Интегрировать автоматический запуск через CTest**: Описать конфигурацию тестовых сценариев в `CMakeLists.txt`, распределив их по классам эквивалентности и граничным условиям.

---

## ⚙️ Архитектура тестового покрытия

Для функции вычисления факториала реализованы три изолированных Unit-теста, проверяющие ключевые бизнес-требования:

1. **`DefaulUse` (Позитивный сценарий)**: Проверка корректности вычисления факториала для стандартных значений (например, $5! = 120$) и граничного значения нуля ($0! = 1$).
2. **`NegativeDgt` (Негативный сценарий)**: Проверка реакции функции на передачу отрицательного числа (ожидаемый возврат `-1` как маркер ошибки).
3. **`Overflow` (Защита от переполнения)**: Проверка перехвата критических значений ($n > 12$), которые приводят к выходу за границы разрядной сетки типа `int` (ожидаемый возврат `0`).

## ⏱ Классификация видов тестирования (Теория)

| Уровень / Вид | Что проверяет на практике | Сложность реализации |
| :--- | :--- | :--- |
| **Модульные (Unit)** | Изолированная проверка логики отдельных функций (текущая работа). | Низкая |
| **Интеграционные** | Корректность взаимодействия нескольких модулей между собой или внешними сервисами (БД, API). | Средняя |
| **Smoke-тесты** | Проверка ключевой работоспособности критических функций системы сразу после сборки. | Низкая |
| **Сквозные (E2E)** | Полное симулирование цепочки поведения пользователя в контексте всего работающего приложения. | Высокая |

> **📌 Концепция BDD (Behavior-Driven Development):**
> Методология, меняющая вектор разработки: сначала на основе требований пишется сценарий ожидаемого поведения (тест), и лишь затем пишется минимально необходимый программный код, удовлетворяющий этому поведению.

## 🚀 Инструкция по автоматической сборке и запуску тестов

Сборка проекта и запуск Unit-тестов выполняются через штатные утилиты автоматизации CMake и CTest:

```bash
# 1. Конфигурация проекта в изолированной папке build
cmake -B build

# 2. Компиляция библиотеки и тестового исполняемого файла
cmake --build build

# 3. Переход в папку сборки и запуск всех тестов через CTest
cd build
ctest --output-on-failure
```

*Флаг `--output-on-failure` заставит CTest вывести в консоль подробные логи выполнения программы только для тех тестов, которые завершились с ошибкой (вернули не `0`), что значительно облегчает локализацию багов.*
